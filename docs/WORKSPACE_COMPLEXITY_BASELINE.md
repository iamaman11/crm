## Initial evidence-based observations

1. The workspace contains 100 packages, of which 86 are technical crates and 13 are business modules. This confirms that technical package growth must be governed independently of business-module growth.
2. `crm-module-sdk`, capability/query runtimes, Protobuf contracts and `crm-core-data` are broad reverse-impact surfaces. Changes to them should default to a broad affected closure.
3. Twenty-eight packages have exactly one direct internal consumer. They are candidates for later review, not automatic consolidation.
4. Workflow path filters currently contain 847 manually maintained entries. This supports generated or catalog-derived affected-check selection after the baseline is stable.
5. Fourteen workflows provision PostgreSQL services. Runtime duration and database-reset telemetry are required before choosing template databases, sharding or larger runners.
6. The Application Runtime workflow has the largest timeout and path-filter surface. It is the first candidate for critical-path decomposition, not immediate test removal.

## Limitations and next measurements

- Build and test durations require repeated runtime telemetry and are not inferred from timeout values.
- Queue time, execution time, cache hit rate, migration/reset time, flake rate and compute totals are not yet included in this static snapshot.
- Reverse impact is computed from declared direct workspace dependencies in `cargo metadata`; contracts, migrations, frontend and operational coupling require separate mappings.
- Current values do not establish blocking budgets.
- A stable Phase B baseline requires repeated reports across representative leaf, owner, shared-core and workflow-only PRs.

The next Phase B packet should collect GitHub Actions critical-path telemetry and correlate workflow runs with changed paths and package closure. Only after repeated evidence may relative warnings or budgets be proposed.
