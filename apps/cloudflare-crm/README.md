# CRM — простой тестовый пилот на Cloudflare

Целевая архитектура: React 19 + Vite Static Assets → **один нативный Worker `workers-rs`** → одна D1. У публичного API нет JS-маршрутизатора, JS-бизнес-бэкенда или второго Worker. Оригинальный Rust `crm-parties` владеет доменом Party; четыре пилотных тестовых раздела обслуживает нативный Rust-адаптер.

Клиенты, контакты, сделки и задачи: создание, просмотр, редактирование, поиск и удаление. Все данные тестовые. Вход — существующий Cloudflare Access, при первом человеческом входе создаётся пустое рабочее пространство.

- Нативный API: `rust-party/src/lib.rs` и `rust-party/src/pilot.rs`
- UI: `web/src/main.jsx`, `web/src/styles.css`
- D1: `migrations/0001_initial.sql`
- Cloudflare: `wrangler.jsonc`
- Тесты: `npm run doctor`, native workerd/Chromium и защищённые GitHub Actions; UI-сборка: `npm run build`

GitHub Actions доверенной ветки публикует Worker + Static Assets и применяет D1-миграцию. https://crm-dev.crm-5bd5e1e1.workers.dev

Усиленная защита и дополнительные инфраструктурные механизмы — после реального production.

После публикации GitHub Actions запускает реальный Chromium на опубликованном URL: клиент → контакт → сделка → задача → обновление страницы → поиск → правки → мобильный экран → удаление. Технический вход используется только для пилотного E2E.

Технические входы `crm-e2e-a` и `crm-e2e-b` имеют разные рабочие пространства. Браузерная приёмка проверяет, что пользователь видит и изменяет свои записи, но не записи другого пользователя.

В разделе «Сделки» есть переключатель «Таблица / Воронка». Воронка показывает пять этапов, число и сумму сделок по каждому этапу. Этап можно поменять прямо на карточке без открытия формы; изменение сохраняется в D1 и переживает обновление страницы. На телефоне колонки идут вертикально.

## Быстрые исправления и диагностика для разработчика

Каталог `shared/catalog.mjs` задаёт поля React и пути к их единственным нативным Rust API-обработчикам. `npm run locate -- deals` (или `contacts`, `tasks`, `INVALID_INPUT`) без сети выводит JSON с ответственными файлами: конфигурация, интерфейс, API, валидация, миграция, unit-тесты, браузерная приёмка. `npm run doctor` проверяет локальную D1-схему и соответствие полей каталогу, не изменяя данные. В CI он запускается до тестов и сборки.

Авторизованный нативный `GET /api/doctor` проверяет D1, подписанный Access JWT, возвращает реальный Git SHA, Worker version и состояние модулей. Проверки, не выполненные самим doctor, честно обозначаются `NOT_TESTED`. Ошибки API имеют `x-crm-error-code` и `x-request-id`: тот же идентификатор связывает реальный HTTP-ответ, аудит D1 и структурированные Cloudflare Logs; длительность обработки записывается в Worker Logs. При ошибке интерфейс показывает код и идентификатор запроса.

Новых сервисов, новых таблиц и отдельной админ-панели нет. Локальное измерение `duration_ms` не включает запуск npm/Node и сетевые задержки; для GitHub/Cloudflare и полного Chromium E2E гарантировать миллисекунды невозможно.

## Постоянный контракт масштабирования

Для каждого нового сеанса ChatGPT и каждого кодового изменения действует [AGENTS.md](AGENTS.md). Он закрепляет исключительно чат → GitHub → GitHub Actions → Cloudflare, сохранение экспертной сложности CRM внутри самостоятельных модулей, точную принадлежность коду/тестам и обязательный цикл доказательной приёмки. `shared/catalog.mjs:implementationOwners/ownerFiles` позволяют `npm run locate` находить конкретный владеющий модуль по мере роста проекта; `npm run doctor` предотвращает появление новых функций без объявленного источника и тестов. Первые четыре тестовых раздела используют один нативный Rust-адаптер; новые экспертные функции должны иметь собственное расположение. Полная архитектура остаётся одним Worker и D1, пока дополнительная инфраструктура не обоснована измеримой необходимостью.

## Customer 360 — полезная карточка и первая независимая композиция

В «Клиенты» кнопка «Карточка» показывает контакты, сделки, задачи, просрочку и итоговую сумму по одному клиенту. Read-only композиция реализована в `rust-party/src/pilot.rs`, её UI — `web/src/Customer360.jsx`. Дублирующий JS-модуль удалён. Исходные данные остаются в четырёх существующих D1-таблицах, всё tenant-scoped. `GET /api/customer360/:id` требует Cloudflare Access, неизвестный и чужой ID → 404. Вывод ограничен 100 записями каждой категории, точные общие счётчики считаются отдельно, неполные производные метрики обозначены «—». Команды `npm run locate -- customer360` и `npm run doctor` показывают владельца модуля и подтверждают read-only контракт без фиктивной таблицы. Изменение связанных записей — через существующий CRUD. Приёмка — Chromium desktop/mobile + A/B изоляция + unit-тесты.

## Полный диагностический цикл нативной модели

1. Авторизованный `GET /api/doctor` **без записи** проверяет реальную опубликованную версию Workers-rs (Git SHA и Cloudflare version id), подписанный Access, наличие девяти таблиц D1, tenant-scoped чтение клиентов/контактов/сделок/задач/Party и наличие колонки `crm_audit.request_id`. Отсутствующее состояние возвращает FAIL/HTTP 503. `doctor` **не утверждает**, что выполнил UI или запись: они отмечены как внешние проверки CI.
2. Защищённый main-only GitHub Actions выпускает именно собранный в CI Rust/WASM + React, проверяя SHA/хеши, и проводит полный Chromium E2E на **основном** адресе, включая кнопки всех тестовых разделов, отмену, ошибки, повтор, A/B и мобильную версию.
3. `e2e/live.mjs` сохраняет `.release/native-functional-cycle.json` с реальными UI-ответами и `x-request-id`, а `scripts/deploy.mjs verify-data` независимо сверяет **все** успешные UI-мутации с `crm_audit` и Cloudflare Logs той же версии Worker.
4. Релиз принимает только полный PASS и сохраняет `.release/native-functional-accepted.json` в GitHub Actions artifact. При ошибке приемки Worker возвращается к предыдущей версии; D1 не откатывается автоматически и это отражено в отчёте.

Обслуживаемый API не зависит от Node/JS. Старый `worker/index.mjs`, `worker/unified.mjs` и их тесты удалены. Разрешён только стандартный glue-код, который автоматически создаёт Rust/WASM toolchain.
