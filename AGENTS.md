Единственный канонический источник — [iamaman11/crm](https://github.com/iamaman11/crm), рабочая ветка CRM [dev](https://github.com/iamaman11/crm/tree/dev). Перед работой прочитать актуальный remote HEAD и правила, не восстанавливать состояние по памяти чата. Цель — промышленная Autonomous Revenue CRM мирового уровня: постоянный функциональный скелет, затем развитие до 10/10 по продуктовому плану, не временный MVP.

## Порядок работы

1. Проверить remote dev, архитектуру, #484 и текущий курсор. Для технической задачи дополнительно открыть профильный #485/#486. Сверить состояние CI и опубликованный SHA отдельно.
2. Проверить уже принятую функцию, её реальных потребителей и действующий typed owner/RPC/UI/tests. Для продуктового пробела сопоставить соответствующие исторические операции и негативные тесты; оформить A/B/C/D по правилам приложения до кода. Исторический OPEN не является приказом реализовать. Сохранить полезную семантику, не копировать legacy.
3. Работать крупными связанными вертикальными срезами. Обычная одиночная работа завершается одним атомарным code push в `dev`. Для параллельного пакета координатор фиксирует состав, общую базу, границы задач и приёмку в #489. Обычная функция расширяет существующий owner, а новая граница требует обоснования.
4. Соблюдать единый типизированный путь и штатный CI приложения. Для каждой рабочей ветки с кодом обязателен Writer Gate A на её точном SHA. Writer Gate B назначается в ТЗ, когда сценарию нужно отдельное доказательство на живом preview. Исполнитель передаёт SHA и результаты применимых проверок. Детали Gate A и B описаны в [правилах приложения](apps/cloudflare-crm/AGENTS.md). Измерения и изменения CI ведутся в #486.
5. Каждый исполнитель получает одну задачу, свою ветку и отдельный checkout или worktree от одной принятой базы `dev`. Договорённости о файлах, контрактах, миграциях и общих тестах фиксируются до старта. Состояние локальной D1, сборок, портов и временных артефактов раздельное. В доверенном пакете границы ролей организационные. Если пакет требует технического разделения прав, координатор проверяет его в фактических средах. Общие зависимости решает координатор.
6. Координатор принимает ветки со статусом `READY_FOR_HANDOFF`, сверяет их изменения и запускает один preflight объединённого SHA в `integration/parallel/*` с пропуском деплоя. Смысловой конфликт возвращает владельцу задачи. После PASS сверяет актуальный `origin/dev` и обновляет его fast-forward. Если база изменилась, проверяет обновлённый кандидат. Продуктовый результат `ACCEPTED` требует Production Gate A и независимого Production Gate B на одном опубликованном SHA. При сбое опубликованного релиза координатор ведёт восстановление по #485.
7. Не скрывать blockers, неопределённость и принятые без прямого указания решения. Не заявлять готовность без evidence. Не поручать пользователю штатные команды/браузерную приёмку, если доступный инструмент позволяет выполнить их самостоятельно.

## Границы и история

Активный runtime — apps/cloudflare-crm, один Rust Worker, generated Connect, одна D1, React как проекция Rust. Исходные domain owners остаются единственными владельцами бизнес-инвариантов. PostgreSQL/SQLx/RLS, services/crm-api и прежний процессный runtime не восстанавливать. Исторические исходники и тесты не удалять без пооперационного A/B/C/D и проверки потребителей.

[docs/archive](docs/archive/) и закрытые/исторические issues — справочные материалы, не действующие инструкции. [Предыдущая редакция корневого AGENTS.md (не нормативная)](https://github.com/iamaman11/crm/blob/c69f1e1beb621c22b907c877cfdb5cf6ec88c25f/AGENTS.md) сохранена в Git history целиком. Никаких новых старых packet/PR/CI процессов из неё не переносить. Штатная машинная packet-проверка активного dev остаётся частью существующего workflow; старый origin/main процесс не применяется.
