## Порядок работы

1. Проверить remote dev, архитектуру, #484 и текущий курсор. Для технической задачи дополнительно открыть профильный #485/#486. Сверить состояние CI и опубликованный SHA отдельно.
2. Проверить уже принятую функцию, её реальных потребителей и действующий typed owner/RPC/UI/tests. Для продуктового пробела сопоставить соответствующие исторические операции и негативные тесты; оформить A/B/C/D по правилам приложения до кода. Исторический OPEN не является приказом реализовать. Сохранить полезную семантику, не копировать legacy.
3. Работать крупными связанными вертикальными срезами, не смешивать независимые изменения и не публиковать серию микрокоммитов в `dev`. В обычном одиночном режиме сохраняется прямой атомарный code push в `dev`. Параллельный batch допускается только после полного Definition of Ready в #489: writers работают во временных ветках, а в `dev` публикует только координатор после проверки объединённого candidate. Не переписывать доказанное A. Обычная функция расширяет существующий owner; новая граница — только с обоснованием.
4. Соблюдать единый типизированный путь и штатный CI приложения. Не ослаблять правила ради PASS или скорости. В параллельной работе каждый writer обязан лично получить Gate A PASS и независимый LIVE Gate B PASS на одном exact SHA собственной feature-ветки. Эти два результата полностью завершают задание writer: после статуса `READY_FOR_HANDOFF` он передаёт ветку координатору и больше не отвечает за интеграцию или production-приёмку. Координатор принимает только такие handoff, объединяет ветки и выполняет на integration SHA обязательный candidate preflight (существующий build/test workflow, deploy SKIPPED); это проверка совместимости объединения, а не Production Gate A и не продолжение задания writer. После fast-forward в `dev` координатор обязан выполнить **Production Gate A** на exact опубликованном SHA: полный `cloudflare-crm-spike.yml` — CI job PASS плюс `deploy-crm-dev` PASS, публикация того же sealed artifact, проверка source SHA/Worker version, опубликованный smoke и physical D1 receipts/audit/traces. После Production Gate A координатор отдельно выполняет **Production Gate B** через Universal Browser MCP на реальном `crm-dev`, с независимыми пользовательскими сценариями и readback физической D1. Оба production gate относятся к одному exact `dev` SHA; любое изменение SHA требует повторить оба. Branch gates и production gates не заменяют друг друга. Пока per-branch A+B и безопасный branch preview не обеспечены (PRE-02/PRE-07 в #489), parallel batch — NO-GO. Для CI-only работы измерения и решения — #486; не заявлять новую продуктовую приёмку.
5. Только для batch, явно допущенного по #489: каждый writer получает отдельный checkout/worktree, CWD и временную ветку от одного frozen green base SHA; одно полное ТЗ, фиксированный write scope и отсутствие пересечения изменяемых файлов. Агенты не общаются, не ждут друг друга, не меняют чужой scope, не push/merge в `dev`, не деплоят и не получают Cloudflare credentials или прямой доступ к remote D1. Каждый writer лично выполняет Browser MCP Gate B на branch-preview своего точного SHA; preview, отдельный Worker, отдельную D1, Access и read-only D1/receipt evidence создаёт и удаляет только доверенная защищённая automation/координатор с собственными scoped secrets. `crm-dev` и его физическая D1 не используются для branch Gate B. Если preview/evidence отсутствуют, writer фиксирует BLOCKED и не передаёт ветку. Handoff фиксирует base/head SHA, scope, Gate A run, preview Worker/version, Gate B сценарии и D1 evidence. Если удалённое право на запись ограничить по исполнителю невозможно, координатор передаёт исходный Git bundle, а исполнитель возвращает bundle своей ветки. Для этого режима рабочая среда исполнителя должна быть без подключения GitHub с правом записи и без credentials Cloudflare. Координатор проверяет отказ записи из каждой рабочей среды. Сборка, Wrangler D1, порты и временные артефакты изолированы по средам. Обычная одиночная работа не переводится на feature branches автоматически.
6. В параллельном batch координатор принимает writer branch только при `READY_FOR_HANDOFF` (Writer Gate A + Writer Gate B PASS на одном exact SHA). Координатор создаёт одну временную integration branch от frozen base, последовательно включает принятые branches и проверяет итоговый diff; разрешены только механические additive conflicts, семантический конфликт возвращается владельцу. На объединённом exact SHA выполняется один candidate preflight существующим workflow по одному push в `integration/parallel/*`; deploy обязан быть SKIPPED. Этот preflight проверяет совместимость объединения и не является Production Gate A. После PASS координатор сверяет актуальный `origin/dev` и делает один fast-forward push без переписывания истории. На опубликованном `dev` координатор лично получает Production Gate A (полный CI + публикация exact sealed artifact + штатные deployed smoke/D1/trace checks) и затем независимый Production Gate B (Browser MCP + физическая D1) на одном exact SHA. Только после обоих PASS координатор отмечает результат `ACCEPTED`. При FAIL/UNCERTAIN `ACCEPTED` запрещён; координатор ведёт recovery, а если исправляется код writer, возвращает ему точный дефект и требует новый writer A+B на новом SHA. Если `dev` изменился после Production Gate A, оба production gate повторяются. В одиночном режиме сохраняется прямой процесс публикации в `dev` и Production Gate A → Production Gate B.
7. Не скрывать blockers, неопределённость и принятые без прямого указания решения. Не заявлять готовность без evidence. Не поручать пользователю штатные команды/браузерную приёмку, если доступный инструмент позволяет выполнить их самостоятельно.

## Границы и история

Активный runtime — apps/cloudflare-crm, один Rust Worker, generated Connect, одна D1, React как проекция Rust. Исходные domain owners остаются единственными владельцами бизнес-инвариантов. PostgreSQL/SQLx/RLS, services/crm-api и прежний процессный runtime не восстанавливать. Исторические исходники и тесты не удалять без пооперационного A/B/C/D и проверки потребителей.

[docs/archive](docs/archive/) и закрытые/исторические issues — справочные материалы, не действующие инструкции. [Предыдущая редакция корневого AGENTS.md (не нормативная)](https://github.com/iamaman11/crm/blob/c69f1e1beb621c22b907c877cfdb5cf6ec88c25f/AGENTS.md) сохранена в Git history целиком. Никаких новых старых packet/PR/CI процессов из неё не переносить. Штатная машинная packet-проверка активного dev остаётся частью существующего workflow; старый origin/main процесс не применяется.
